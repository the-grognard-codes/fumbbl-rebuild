## Structural leads to audit

1. **One lock for the whole server.** `BrowserV2Adapter.receive`, `disconnect`
   and `expireDecisions` are all `synchronized`
   (`BrowserV2Adapter.java:84,88,518`), and `BrowserV2Runtime.java:55` builds
   one adapter. Every request from every match, including envelope parsing,
   authentication and the JDBC checkpoint writes, therefore runs one at a time.
   This is simple and correct for a small server, but it means one slow database
   write or provider call stalls every match. No ADR records this choice. *Audit:*
   confirm which I/O happens while the lock is held, then either record the
   choice in an ADR or plan per-match serialisation.
2. **A `match` ↔ `local` package cycle.** `local` is meant to be transport;
   `match` is the domain. But `match` imports `local` in six files: five import
   `BrowserRequestTiming` (diagnostics leaking into persistence, e.g.
   `JdbcRecoveryRepository`, `BoundedJsonStorageCodec`), and one imports
   `BrowserTeamJson`. *Fix direction:* put timing behind an interface owned by
   `match`.
3. **Very dense lines.** The browser has 191 lines over 300 chars and the Java
   layer has 90 lines over 200 chars (e.g. `saved-team-protocol.ts:29-30` packs
   a whole JSON parser onto two lines). This is a review and diff hazard rather
   than a defect, but it hides bugs in exactly the protocol and decoding code
   that the "server is authoritative" invariant depends on. Consider a formatter
   gate.
4. **Broad catches.** There are 59 `catch (Exception|RuntimeException|Throwable)`
   in `match`/`local`. Most of the swallowed ones guard diagnostics observers,
   which is reasonable. The broad catches in `MatchJson` (8), `SetupApplication`
   (7) and `FirebaseV2PrincipalAuthenticator` (5) need a check that they do not
   turn a corrupt record or an auth failure into a default.
5. **158 `as` casts in the browser.** The code has no `any`, but these casts are
   where decoded server data could be trusted without a check.

## Repository hygiene

- `.notes/` (741 MB on disk, 1,132 tracked files, 709 of them under
  `overhaul-analysis/`) and `test-output/` (126 MB, 90 PNGs) are tracked. The
  pack is 2.1 GiB. This slows clones and CI, and adds noise to every code
  search. Decide what is evidence worth keeping and move it to an artifact store
  or Git LFS.
- `.git/objects` holds leftover `tmp_obj_*` garbage (`git gc --prune=now`
  clears it).
- `ffb-client-logic/ChangeList.java` was the most-churned file overall (244
  commits) and is now gone. Some tooling or docs may still refer to it.

**Stale Eclipse-compiled class files in Maven's `target/`.** The full run failed
on `SetupSessionTest.selectedSolidDefencePlayerCanBeRedeployedAndConfirmed` with
`var cannot be resolved to a type`. That text is a stub the Eclipse compiler
(ECJ) writes when compiling at a pre-Java-10 language level; javac never
produces it. The class file was dated 2026-11-08 13:57, newer than its source,
so Maven's incremental compile skipped it. An IDE Java language server writing
into `target/` is the likely source (VS Code was running). The risk is that
local test results can disagree with CI. *Fix direction:* point the IDE's
output away from `target/`, or set its Java compliance to 21, and run the full
local validation with `clean`.
