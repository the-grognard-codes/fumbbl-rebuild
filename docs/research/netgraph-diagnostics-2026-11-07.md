# Browser diagnostics overlay: netgraph research

Research date: 2026-11-07. Scope: primary-source inspiration and measurement constraints for a browser-client feature request; no implementation or repository architecture audit.

## Verified reference behavior

The requested search term was `cl_netgraph` in Half-Life / Counter-Strike. The directly verified Valve Source reference implementation calls its control **`net_graph`**. It includes FPS and ping readouts, inbound/outbound traffic, optional loss/choke, latency and interpolation graphs, payload breakdown modes, position, height, font scaling, text visibility, and graph scale controls. It stores a fixed 1,024-sample history. These are useful design precedents rather than a browser-compatible metric contract. The examined source does not establish `cl_netgraph` as a historical Valve command; use “netgraph-inspired diagnostics” in the feature request rather than claiming that spelling is canonical across Half-Life and Counter-Strike releases. [Valve Source SDK implementation](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/vgui_netgraphpanel.cpp)

Valve's current Counter-Strike 2 / Deadlock telemetry HUD supports per-metric Never, Always, or only poor conditions, with configurable warning thresholds. Its FPS is an average, while the frame-time readout reports the worst recent frame; those deliberately expose different problems. Its network graph uses one bar per message, time-varying bar heights, and explicit impairment markers. Its missed-tick metric differs from raw packet loss. Borrow the compact simultaneous presentation and ability to spot spikes; these engine-specific measurements should not be copied without equivalent instrumentation. [Valve Steam Support: Source2 Telemetry HUD](https://help.steampowered.com/en/faqs/view/5E6F-5B36-5485-F6B9)

## Browser measurement constraints

WebSocket JavaScript exposes application messages, connection state, and `bufferedAmount`, but does not expose raw network access or protocol Ping/Pong frames. `bufferedAmount` counts queued application bytes; it excludes framing overhead and operating-system/network-hardware buffers. Consequently an overlay can honestly report application payload rates and the browser's queued outgoing bytes, not actual wire bandwidth. [WHATWG WebSockets interface and buffering](https://websockets.spec.whatwg.org/#the-websocket-interface), [Ping/Pong API limitation](https://websockets.spec.whatwg.org/#ping-and-pong-frames)

The baseline WebSocket protocol runs over TCP. Combined with the restricted browser API, this means missing application responses or unusually long gaps do not establish a measurable network packet-loss percentage, choke percentage, retransmission count, or directional transport delay. A timeout is a timeout, and an application stall may include scheduling or server work. [RFC 6455 overview](https://www.rfc-editor.org/rfc/rfc6455#section-1.2), [WHATWG API surface](https://websockets.spec.whatwg.org/#the-websocket-interface)

`requestAnimationFrame` callbacks normally follow display refresh and commonly pause in hidden tabs. Callback cadence is therefore a useful browser presentation-opportunity signal, not proof that each callback produced a displayed game frame. Use existing renderer frame instrumentation when available; label a callback-based fallback precisely. [Mozilla requestAnimationFrame documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

High-resolution timing provides monotonic duration measurement. Long-task observation can identify main-thread tasks of at least 50 ms, but support must be detected; the current Long Tasks specification is a discontinued draft. Treat this as optional enrichment. [W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/), [W3C Long Tasks API](https://www.w3.org/TR/longtasks-1/)

## Proposed feature shape (design recommendations, not Valve behavior)

- **Debug options:** default Off, Compact numbers, or Numbers + scrolling graph. Offer independent render, latency, traffic, and queue tracks; position/scale controls; optional configurable warning thresholds. An eventual “show on poor conditions” option needs continued bounded sampling while hidden and should state that overhead explicitly.
- **Rendering:** show average renderer FPS alongside worst and p95 frame interval over a stated recent window. Show the sample count/window. Keep renderer CPU time separate from total frame interval if both are instrumented. Do not present a fixed 60 FPS target as universally correct on high-refresh displays.
- **Latency:** use a correlated application-level echo on the existing game connection and local monotonic timestamps. Label the result **application RTT (ms)**: it includes browser scheduling, socket queues, transit, and server response scheduling. Do not halve it into separately labeled upload/download latency. If measured server receipt-to-response duration becomes available, display **server handling (ms)** separately; any RTT-minus-handling figure remains an estimate, not one-way latency. Reuse existing heartbeat/probe instrumentation only after checking its semantics.
- **Traffic:** measure already serialized outgoing and incoming payload sizes once at the connection boundary. Report UTF-8 bytes for text and byte length for binary; show in/out KiB/s and messages/s over a stated interval, lifetime counters if useful, current/peak `bufferedAmount`, connection state, and age of last message. Quiet turn-based traffic is valid and must not automatically become a connection warning.
- **Scrolling histogram:** specify this as a chronological scrolling bar chart, newest sample at the right, with time on the horizontal axis and explicit units on each vertical scale. Use aligned tracks for frame interval, RTT, and inbound/outbound payload volume; avoid combining ms and KiB on one unlabeled axis. Distinguish idle/empty buckets, timeouts, disconnected gaps, hidden-tab gaps, and genuinely unavailable measurements from zero. A latency distribution histogram could be a later separate view.
- **Bounds and overhead:** a concrete starting budget is 60 seconds of history, 250 ms aggregation buckets (240 buckets per track), overlay repaint at most 4 Hz, and at most one application RTT probe per second with one outstanding probe and a finite timeout. Keep per-frame/per-message work to counters and fixed-size aggregates; compute quantiles only on bounded data. These numbers are proposed defaults to validate, not performance guarantees. No payload retention, raw message logging, unbounded performance entries, or per-frame React state commits.
- **Lifecycle:** when Off, stop overlay observers, timers, and optional probes; when hidden, pause optional probes and redraws, mark the history gap, and reset timing baselines on return. Disconnect/reconnect must invalidate outstanding correlations and mark the graph boundary. Keep only bounded numeric history in memory and ensure disabling/re-enabling cannot duplicate subscriptions.

## Verification recommendations

Use deterministic tests for UTF-8/binary accounting, rolling-window expiry and ring-buffer caps, RTT correlation/timeout/reconnect behavior, hidden-tab gaps, and unsupported performance APIs. Exercise Unicode messages and quiet sockets. Visually check compact/full layouts and spikes at normal and high display refresh rates. Profile a repeatable active-match or replay scenario with diagnostics Off and On, documenting CPU/frame-time and memory impact; acceptance should require no steady memory growth and no material overlay-induced regression under the chosen reference scenario.

## Evidence limits

Valve's developer wiki pages returned HTTP 403 during this research, so they were not used as evidence. The Half-Life/Counter-Strike naming clarification is deliberately limited to the available official Source SDK and current Valve support reference; it is not a claim that every historical GoldSrc/Source console variant was exhaustively checked.
