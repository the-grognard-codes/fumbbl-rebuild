# Authoritative match window and gameplay parity

Issue: [#53](https://github.com/the-grognard-codes/fumbbl-rebuild/issues/53).

Status: ready for implementation. Product decisions confirmed by the owner on 2026-09-27.

## Problem Statement

The signed-in browser match uses the real game server, but its presentation and interaction differ from the approved bottom-ribbon MVP preview. The current screen can scroll past the pitch and bench, leaves too much space to generic controls, and lacks the preview's route planning, action ribbon, dice, match log, and chat. The preview itself uses illustrative teams, routes, outcomes, and messages. Coaches need that layout and flow with authoritative BB2025 decisions; spectators need the same public action sequence without gameplay controls.

## Solution

Make the [approved bottom-ribbon preview](https://github.com/the-grognard-codes/fumbbl-rebuild/blob/main/browser-client/test-output/pitch-preview/full-route.png) the visual reference for the authenticated match. Preserve its art, pitch geometry, compact dugouts, scoreboard, sidebar, and bottom ribbon while binding every displayed fact and every committed choice to the game server. Support partial and multi-square movement paths, explicit action selection, contextual decision popups, pitch dice, a complete durable event log, match chat, and replay of the resulting sequence. Keep two coaches and authorized spectators synchronized through the versioned browser protocol.

## User Stories

1. As a coach, I want the scoreboard, pitch, dugouts, sidebar, and action ribbon visible together, so that I can play without page scrolling.
2. As a coach, I want the match window to retain the approved art and typography, so that live play looks like the MVP preview.
3. As a coach, I want my match team's name and resources shown accurately, so that the scoreboard represents the match I joined.
4. As a coach, I want each player shown with the correct sprite, jersey number, status, attributes, and skills, so that I can make informed decisions.
5. As a coach, I want compact reserve, KO, casualty, and other off-pitch counts with an expandable roster, so that the pitch stays large while every player remains accessible.
6. As a spectator, I want the same public board and event sequence in a read-only layout, so that I can follow the match without disabled coach controls.
7. As a coach, I want to select a player and see only currently legal actions, so that I do not guess what the engine permits.
8. As a coach, I want Move, Block, Blitz, Last used, and More actions in the ribbon, so that common and recent choices are quick to reach.
9. As a coach, I want Last used to recall my most recently committed More action in this match, so that I can repeat it when it remains legal.
10. As a coach, I want More actions to contain every currently eligible non-star BB2025 action, so that the compact ribbon does not remove game capabilities.
11. As a coach, I want explicit special-action combinations such as Blitz–Stab or Foul–Chainsaw when legal, so that I know which attack I am declaring.
12. As a coach, I want Target Assist to select a matching server-offered action without committing it, so that selecting a target is helpful but safe.
13. As a coach, I want to explicitly activate Blitz against an adjacent opponent, so that Target Assist does not silently replace a Block with a Blitz.
14. As a coach, I want to construct a movement path by clicking successive waypoints, so that I control the route before committing.
15. As a coach, I want a distant waypoint to fill a smart span from my previous waypoint, so that I can plan several squares with few clicks.
16. As a coach, I want to click an earlier waypoint, Undo, or Clear to revise the route, so that a mistaken segment is easy to correct with pointer, keyboard, or touch.
17. As a coach, I want the planner to avoid rolls and possible opponent reactions when an open route exists, so that the default route reflects the safest obvious choice.
18. As a coach, I want the planner to rank unavoidable risky routes by reroll-free completion chance, then fewer rolls and shorter distance, so that its choice is predictable.
19. As a coach, I want a manual route even when it is less safe, so that tactical positioning remains my decision.
20. As a coach, I want each path square to show required dodge and rush targets and possible reactions such as Diving Tackle, Tentacles, or Shadowing, so that I understand the route's hazards.
21. As a coach, I want to commit any legal portion of my remaining movement, including permitted rushes, so that I can stop short and later declare another path.
22. As a coach, I want one Commit to execute my planned path square by square, so that I do not have to confirm each ordinary movement square.
23. As a coach, I want a required reroll, skill, or opponent-reaction decision to pause the route, so that the correct person can answer it.
24. As a coach, I want a resolved prompt to resume the remaining valid path automatically, so that I do not have to redraw it.
25. As a coach, I want an invalidated remaining path to stop at the last confirmed square, so that I can make a fresh plan from the actual board.
26. As a viewer, I want the player to move through every confirmed square in order, so that the action is understandable rather than an instant teleport.
27. As a viewer with reduced-motion settings, I want ordered square-to-square updates without sliding animation, so that the same information remains accessible.
28. As a reconnecting coach or newly joined spectator, I want the current confirmed board immediately, so that I do not have to play through missed animation before watching live.
29. As a coach, I want graphical popups for coin choice, receive/kick, block and skill decisions, rerolls, and other required prompts, so that decision controls do not occupy permanent pitch space.
30. As a coach, I want multi-player choices such as Quick Snap to use one click to select and another to deselect, with a visible limit and Confirm, so that I can review the full choice before sending it.
31. As a coach, I want End Turn confirmation while I still have unactivated players, so that I do not forfeit actions by accident.
32. As a viewer, I want the actual rolled dice shown on the game area without hiding the blocking player, so that I can follow the action visually.
33. As a chooser, I want the valid block die or reroll option selectable from the displayed dice and prompt, so that the visual choice commits the server's offered decision.
34. As a viewer, I want the log to record every accepted player decision and every roll, result, modifier, target number, and reroll source, so that I can understand how a play resolved.
35. As a viewer, I want block dice, selected die, armor, injury, casualty, apothecary, regeneration, foul, send-off, argue-the-call, bribery, corruption, and between-drive KO recovery recorded when they occur, so that the log covers the whole match.
36. As a viewer, I want movement and push records to show starting and ending coordinates without logging each intermediate coordinate, so that the history remains readable.
37. As a coach or spectator, I want to send and read match chat with sender identity and server time, so that I can communicate during the match.
38. As a returning viewer, I want the complete log and chat after reconnect, so that a dropped connection does not erase context.
39. As a replay viewer, I want to seek by turn or event, change replay speed, and skip playback animations, so that I can inspect a completed match efficiently.
40. As a replay viewer, I want dice, selected choices, log entries, chat, and authoritative board state aligned at the chosen event, so that replay explains what happened without rerunning the engine.
41. As a keyboard user, I want focusable action, path, dice, popup, and log controls with text equivalents for colors and patterns, so that I can play without relying on hover or color alone.

## Implementation Decisions

- The approved preview is a presentation reference. Its sample state, local route rules, assumed successes, chat messages, and resource counts never become live match data. The live match uses the existing DOM/SVG pitch and art, with a shared presentation interface fed by an authoritative match adapter. A separate preview adapter may keep the illustrative fixture.
- Preserve the accepted 26×15 square pitch, square cells, anchored sprites, and shared Fit/zoom/pan transform. The viewport layout keeps the scoreboard, complete Fit pitch, compact dugouts, sidebar, and ribbon visible together at the preview's 1920×1080 size and at 1920×900, 1920×820, and 1280×660 CSS viewports. Long roster, log, and chat content scrolls internally. The screenshot is the visual reference, with real match text and resources permitted to differ.
- Extend the versioned match projection with match-team names, public player attributes/skills and status, structured off-pitch categories, relevant resources, explicit acting/source-player identity, action variants, and role-appropriate prompt metadata. Use match-team names from the frozen match team, not editable saved-team state. Add strict positive and negative decoder/projection tests and a paired server/browser rollout for each contract version.
- The server remains the only authority for action legality, movement allowance, target numbers, dice, prompts, resource consumption, and outcomes. The client may preview but cannot invent an action ID, roll result, or successful position. Commit and the guarded keyboard shortcut share one mutation path. Hover, unpinned targets, spectator views, disconnected state, stale revisions, and pending requests cannot mutate the match.
- Provide a versioned, read-only route preview from the active BB2025 rules/mechanics. It resolves each coach-selected waypoint and smart span to canonical squares, roll targets, and possible reaction hazards. A distant waypoint plans from the last waypoint; earlier-waypoint selection truncates; Undo and Clear are available. Manual route segments remain allowed if legal, including a tactically suboptimal route.
- Smart-route ordering prefers a route without rolls or possible opponent reactions when one exists. Otherwise compare reroll-free completion chances based on applicable target numbers; use fewer rolls and shorter distance as tie breakers. Available team, skill, or other rerolls never enter route scores or future displayed success percentages. Possible opponent choices are marked separately and are not treated as guaranteed rolls. Show required roll targets now; a trustworthy displayed whole-route percentage is a separate follow-up to issue #37.
- A route commit accepts a server-bound canonical path for the current match revision, actor, active player, and remaining allowance. It may contain fewer squares than the player could move. The server validates again before execution, uses the native multi-square movement command, records each confirmed transition, and pauses on an engine decision. On a successful decision it resumes a still-valid remainder; on invalidation or terminal failure it stops at authoritative state. Repeated partial declarations remain possible while the engine permits movement.
- The action ribbon exposes Move, Block, Blitz, Last used, and a menu of currently offered non-star BB2025 actions. Last used is per coach and match, updates after a committed More action, retains its label while temporarily unavailable, and never bypasses server legality. Explicit combinations such as special Block/Blitz attacks and Chainsaw Foul appear only where the engine validates them. A generic action selector may remain as an accessibility/fallback diagnostic only while every supported action is migrated; it is not the primary match UI.
- Target Assist selects a matching server-offered action and target but never commits. An adjacent opponent defaults to Block; Blitz against that opponent requires explicit coach activation. Required engine choices use themed, focus-managed popups; pitch selection may remain in the ribbon for bounded multi-player choices. Wizard, inducement, and star-specific decisions have presentation hooks but are only exposed when a later workstream makes them reachable in a real match.
- Live movement playback consumes ordered confirmed movement events, not client-predicted success. The transcript may retain intermediate coordinates as playback data, while the visible log summarizes each movement or push with starting and ending coordinates only. Both coaches and spectators see every confirmed square; no live Skip or advance control exists. A prompt pauses presentation at its decision boundary. Reduced-motion presentation uses ordered stepped changes. Reconnect or late subscription starts at the current confirmed snapshot and only plays new events. Replay may seek and change speed.
- Dice use reusable game art and a pitch overlay placed near the event without hiding the blocking player or a required target. A selectable block die maps to the exact server-offered choice. Valid reroll options, including rerolling a successful roll where BB2025 permits it, are shown by the prompt contract. The displayed result persists briefly after resolution; the transcript preserves it permanently.
- Extend issue #42's durable transcript design to record accepted decisions, ordered native reports and dice, movement/push start and end coordinates, server time, role visibility, revision/checkpoint bindings, chat, and terminal result. Keep bounded range/index reads separate from the compact live match projection. The same public facts are visible to both coaches and authorized spectators when revealed by rules; private choices appear only when revealable. Exact retries must not append duplicate events. Completed replay reads reconstruct stored facts and snapshots without engine execution.
- Signed-in coaches and authorized live spectators may send and read match chat. The server assigns identity, timestamp, and order; bounds message size, rate, and retained storage; escapes user text; and broadcasts after durable commit. Chat cannot mutate the game engine. Preserve history, local draft, unread indicator, reading position, and clear connection/send state. Completed replay includes chat under the established public replay policy.
- Preserve the accepted active-match publication ownership: recipient access is rechecked and each viewer gets its permitted state. Durable event ranges supply lossless catch-up because live publication is best effort. Use server-side admission and bounded paging rather than attaching the whole transcript to every state update.
- Technical choices such as snapshot cadence, route-token encoding, message limits, animation timing, and internal component boundaries are implementation decisions, provided they satisfy the observable contracts and existing storage limits. No further product answer is required for these.

## Delivery Slices

1. **Contract and fixture baseline.** Inventory current action and prompt coverage, projection fields, asset mapping, event reports, and viewer permissions. Capture deterministic two-coach/spectator checkpoints for normal movement, dodge/rush, blocked movement, special attacks, kickoff, and crowded 22-player play. Record the approved screenshot and current live screenshots at the target viewports. Define the versioned route/event/action contracts and the one end-to-end test seam. **Done when:** every desired UI field and command has an authoritative source or an explicit contract addition; the fixtures reproduce the baseline gaps.
2. **Authoritative presentation and shell.** Add match-team names, player details, structured off-pitch status, resources, and action-source metadata to the projection. Move the preview's presentational pieces behind a data-and-intent interface; bind the live adapter to server state. Implement the fixed-height desktop grid, compact dugouts, right rail, spectator view, and responsive Fit pitch. **Done when:** screenshots at 1920×1080, 1920×900, 1920×820, and 1280×660 show the full required frame without page scrolling, and no sample text, counts, or outcomes appear in live play.
3. **Action coverage and contextual decisions.** Expose all eligible non-star BB2025 on-turn declarations and validated special-action combinations, including current browser gaps. Replace the generic primary selector with ribbon controls, Last used, More actions, Target Assist, and End Turn confirmation. Present kickoff, block dice, reroll/skill, push/follow-up, Quick Snap and other reachable decisions in graphical prompts or bounded pitch selection. **Done when:** each server-offered action is reachable, role-safe, keyboard accessible, and tested through a real actor/spectator sequence; an adjacent Blitz always requires explicit activation.
4. **Durable ordered event foundation.** Implement the versioned transcript/migration work coordinated with #42: accepted input, native reports, dice, coordinate endpoints, viewer visibility, checkpoints, bounded range/index reads, exact retries, and crash/reconnect behavior. Add a live log that uses this source, including roll arithmetic and all named report families. **Done when:** a two-coach match produces an ordered, durable, spectator-readable log; a restart or duplicate request neither loses nor doubles entries; result replay reaches the same final state.
5. **Authoritative route planning and commit.** Add reroll-free route scoring and possible-reaction metadata, waypoint/span preview, Undo/Clear, remaining movement display, and server-bound multi-square commit. Cover partial paths, repeat declarations, rush allowance, prompts during movement, continued paths, stopped paths, and stale preview rejection. **Done when:** real engine tests demonstrate a six-square three-waypoint route, a safe smart span, a deliberate less-safe route, a partial move followed by another, and dodge/rush/reaction interruptions.
6. **Pitch playback, dice, and replay.** Drive ordered live square transitions and dice overlays from authoritative events; place selectable dice away from the blocking player; keep required prompts over the pitch without layout movement. Extend replay to show the same dice, selected results, log, and board at seekable events. **Done when:** coaches and spectators see matching unskippable live sequences; reduced motion still shows all squares; reconnect shows current state immediately; replay can seek or skip without rerunning the engine.
7. **Chat and history experience.** Complete #42's authenticated chat family with spectator sends, durable order, bounded storage, reconnect and replay reads. Implement chat/log tabs, composer, unread and send states, expanded history, start/latest navigation, and preserved reading position. **Done when:** two coaches and an authorized spectator exchange messages, reconnect without loss or duplication, and see the same persisted chat in completed replay.
8. **Integrated acceptance and dev-local review.** Build paired browser and game-server artifacts, update the dev-local game container when contracts change, and run full signed-in play with two coaches plus spectator. Review visual captures against the approved screenshot, crowded board, action prompts, dice, route hazards, compact windows, keyboard and reduced-motion behavior, reconnect, replay, and failure paths. Record any platform/accessibility or artwork-release evidence that cannot be produced locally without claiming it passed. **Done when:** the integrated dev-local instance is reviewable and the linked issue records the tests, captures, remaining limitations, and any follow-up defects.

Slices 1–3 can establish visual and action parity before the durable log is complete, provided no illustrative content is presented as live data. Slice 4 is a prerequisite for reliable live playback and replay in slice 6. Slice 5 depends on the action contract and feeds slice 6. Slice 7 can proceed after the durable event foundation. No slice changes server authority or upgrades an active match in place.

## Testing Decisions

- The highest-value seam is an authenticated two-coach and spectator match through the public browser protocol, native BB2025 engine, durable store, and browser UI. Test accepted commands, prompts, revision order, public visibility, reconnect, completion, and replay there. Reuse the repository's existing native match integration, browser-hosted match, protocol projection, and result/replay tests as prior art.
- Focused lower-level tests cover the route planner's ordering and hazard metadata against real BB2025 mechanics, canonical path validation, remaining movement, one-time event persistence, typed report formatting, strict decoder rejection, and chat authorization/bounds. Assert observable state and event output rather than private component structure or duplicated mock rules.
- Include server-positive and server-negative projection tests for every new field and audience, especially private prompt timing, accepted/rejected actions, spectator mutation denial, invalid/extra fields, and older retained replay formats according to the chosen migration.
- Exercise normal path, no-roll span, dodge, rush, combined checks, opponent reaction, skill and team reroll, terminal failure, invalidated remainder, partial/repeated movement, and a stale route. The log must show base target, modifier, effective target, raw roll, result, and reroll source; success percentage labels are absent.
- Exercise ordinary and special Block/Blitz/Foul combinations, block dice selection, Pro/Brawler/team rerolls when offered, armor/injury/casualty/apothecary/regeneration, send-off/argue/bribery/corruption, and KO recovery using deterministic engine scenarios. A scenario unsupported by the current match-team catalog must be identified rather than faked.
- Characterize lost replies, duplicate request IDs, reconnect during movement or chat, slow spectator delivery, process restart, crash boundaries around event/chat commit, transcript paging, and storage admission. A client animation or delayed publication must never advance authoritative gameplay.
- Visual checks use deterministic real projection fixtures at the reference and target viewports, with 22-player crowding, a route, a prompt, dice, sidebar history, and long team/player names. Check Chrome and Edge locally, browser zoom, full pitch and ribbon visibility, focus/keyboard behavior, text equivalents, and reduced-motion playback. Record unavailable browser/assistive-technology combinations as untested.

## Out of Scope

- Inducement purchases, Wizard acquisition/use in a real match, star-player recruitment, star sprites and other new art, and unique star abilities. The prompt/action framework must accept their later integration, but they are a separate workstream.
- A displayed per-step or whole-route success percentage. Issue #37 remains the later authoritative percentage contract; when implemented it must exclude every reroll, including skill rerolls.
- Spectator chat restrictions or moderation features beyond basic authenticated identity, server-side bounds, safe rendering, and access checks. The owner intentionally permits spectator sending for now.
- Rich sprite-sheet movement or dice-roll animation, sound, mobile-specific redesign, league administration, and unrelated match-creation changes. Static sprite movement and static dice faces are sufficient here.
- Public deployment, an in-place upgrade of active matches, and changes to browser window closing behavior.

## Further Notes

- This spec extends the completed MVP match window issue #50. It coordinates with #42 for the transcript/chat foundation, #37 for later percentages, and the storage-admission work in #38. The existing active-match publication and match-team ownership ADRs remain authoritative.
- The owner has already resolved the product choices in the interview. No additional owner input is required to begin the slices. Implementers should surface only a genuinely new rule ambiguity or external release gate.
- The existing replay/chat design proposed spectator-read access but left spectator sending undecided. This spec resolves it in favor of authenticated spectator sending during accessible live matches and inclusion of those messages in the completed replay.
