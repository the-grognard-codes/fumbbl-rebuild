# M5 DOM/SVG match GUI: spec and implementation slices

Status: **proposed execution breakdown, 2026-09-25**. The owner selected DOM/SVG for the M5 board in the [ADR-002 addendum](04-technology-and-decisions.md#adr-002-typescript-react-dom-interface-pixijs-board-vite). This plan organizes the already accepted desktop scope; it does not authorize deployment or expand supported BB2025 rules/content. The [pitch requirements](../art-preview/pitch-and-ui-requirements-v2.md) are the visual geometry/layout spec, the [PRD](05-product-requirements.md) defines product journeys, and [R6](m4-workstreams-reference.md#r6--desktop-renderer-accessibility-and-content-release-checks) defines integrated release checks. The [parity review](m5-renderer-parity-review-2026-09-24.md) records the renderer evidence.

## Product contract for the M5 desktop match

- Two authenticated players and an authorized read-only spectator receive audience-appropriate authoritative projections through `/browser/v2`. Shared public state must agree on revision, phase, players, ball, resources, and outcome; prompts, legal actions, event history, and any private data follow each role's existing projection rules. Recipient-specific authorization and projection remain server-owned. The active [v2 contract](../../browser-client/public-api-v2.md), [`V2Client`](../../browser-client/src/v2-client.ts), and [publication ADR](../../docs/adr/0001-active-match-publication.md) are the integration boundaries.
- Match preparation/setup and live play have distinct surfaces. Direct links, reload, reconnect, uncertain-request reconciliation, and setup-to-play navigation follow server state. The existing live DOM `GameView` remains the working baseline while routes are separated.
- The selected board uses the approved 26×15 pitch, one-square end zones, 4/7/4 wide zones, fixed square hit areas, shared Fit/zoom/pan transform, existing Human/Orc PNGs subject to public-use review, and DOM controls around SVG field/overlays. A frozen roster-to-art mapping supplies sprites; missing art becomes a labeled token. The board presents state and emits intents; it does not calculate legal actions, dice, percentages, or outcomes.
- Selected-player, legal-target, path, block/prompt, status, ball, and resource presentations come from current server state and server-issued actions. A proposed path may animate decoratively; action success percentages appear only after the authoritative contract defines their source and whether they are per-step or cumulative and include rerolls. Sprite-sheet action/status animation is a later art/content increment; M5 should preserve a presentation seam for it without requiring new frames for the initial live GUI.
- Visible Commit and the guarded Space shortcut use one command handler. A hover or unpinned/invalid target never sends a command. Pending, stale, rejected, duplicate, disconnected, and spectator states must not cause a second or unauthorized mutation. A local animation never advances a match phase on its own.
- The preview's local coach chat and mock End Turn/results cannot be copied as product behavior. The active v2 protocol has no chat message; show only supported server data and server-issued actions. Keep the preview and parity routes as isolated design/diagnostic evidence.

## First task handoff: M5a

Start with the existing `SetupPanel.tsx`/`GameView`, `V2Client`, `v2-projection.ts`, `public-api-v2.md`, server projection/actions and `supported-actions-v1.json`. Produce a compact mapping for player, ball, score/resources, status, actor/phase, legal action/prompt, role visibility, revision and art identity. Identify where the live UI needs data the current projection does not provide, especially path/odds and frozen roster-to-sprite identity. Then capture the agreed Blitz actor/spectator sequence if a deterministic server scenario exists; otherwise record exactly what fixture or service hook is missing and carry that as an M5d acceptance dependency. Do not start by copying the local parity reducer into the live client.

The expected M5a review artifact is the mapping plus any narrowly required protocol changes and their tests. This makes M5b's route split and M5c's board adapter concrete without reopening the DOM/SVG choice.

## Continuous execution and owner-only gates

M5a through M5e can be implemented in sequence in one continuing task without seeking approval between slices. The agent should complete each slice's checks, save a concise status/evidence checkpoint, then proceed. Routine route names, component boundaries, art fallbacks and narrow contract changes can be decided from the accepted specs and verified code. If the server lacks an authoritative odds contract, omit percentage labels for now rather than ask the owner to approve invented values. If the Blitz fixture is missing, build a deterministic test fixture or record the precise blocked acceptance condition; do not silently substitute the local mock.

M5f's keyboard implementation and automatable checks can continue the same way. Full M5g acceptance may require things the agent cannot produce locally: actual Mac Safari/VoiceOver and other unavailable browser/AT observations, owner/content-review disposition of artwork rights, and any approval to publish or deploy. Inventory and test everything available, mark missing combinations or dispositions as open, and do not claim release acceptance for them. A foreground human visual check of the integrated board can also surface changes to address, but routine fixes need no per-slice approval.

“One sequential go” means a continuous objective with durable checkpoints, possibly spanning multiple sessions or context compactions; it is not a guarantee that the entire 20–40 developer-day milestone will fit in one uninterrupted turn. Do not commit, push, deploy or publish without a separate request. Pause only for a genuine external dependency, an irreversible action, or a choice that materially changes accepted product scope; otherwise keep working through the slices.
