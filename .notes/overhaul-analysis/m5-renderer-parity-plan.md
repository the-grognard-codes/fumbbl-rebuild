# M5 renderer parity plan

Status: **awaiting final design-review confirmation**. The production board renderer remains open under ADR-002. This document records owner decisions for the first M5 slice; the parity results and renderer choice will be recorded after the experiment.

## Agreed experiment scope

- Drive the current DOM/SVG pitch and a Pixi pitch from one immutable local fixture and renderer-neutral interaction model. Keep the existing MVP route intact. The experiment does not connect either renderer to a live match.
- Use a scripted local movement-then-block **Blitz** sequence for the side-by-side interaction, including path/target presentation and a pending block choice. Its outcomes remain clearly labeled mock state.
- Add a separate, read-only mapping check against saved authoritative `/browser/v2` projections from that Blitz sequence: before movement, after movement/target declaration, and at the pending block choice, with acting-player and corresponding spectator views. This check does not send commands or establish live-match acceptance. If the specific authoritative sequence cannot be captured inside the spike timebox, record the gap and do not fabricate a server fixture.
- Require exact agreement on pitch geometry, cell anchoring, overlap order, hit areas, and interaction behavior. Review paired screenshots for a perceptual match; browser-dependent antialiasing need not be pixel-identical. Record intentional differences and unresolved mismatches.
- Demonstrate one representative player movement transition and its path or selection overlay in both renderers, using the existing static sprites. New animation artwork and elaborate effects are outside this spike.
- Preserve the MVP's existing visible controls and keyboard behavior during the spike, but defer a new labeled DOM keyboard/text companion until after the renderer decision. The experiment will not establish screen-reader acceptance. Integrated M5/R6 still owns the accessible companion and full browser/assistive-technology matrix.
- On Pixi startup failure or rendering-context loss, keep a functional labeled DOM grid and action controls with a clear recovery message. The spike does not require maintaining a second polished DOM pitch as a production fallback. Inject and test both failure modes.
- Review the spike after five developer-days. Record passed checks, unresolved questions, and the evidence a specific extension would buy. Missing comparison evidence cannot count as a Pixi win.
- Keep DOM/SVG when both renderers perform comfortably and meet the visual and interaction bar. Select Pixi only for a demonstrated user-visible advantage in the representative crowded movement test (such as DOM missing a 60 fps frame budget while Pixi meets it) or a materially simpler implementation of that animation. Hypothetical future animation value alone is insufficient.
- Veto Pixi for wrong square/player targeting, incorrect overlap order, unreadable sprites or overlays at tested zoom levels, loss of action controls after renderer failure, or reproducible input or memory regression. Record small antialiasing differences without treating them as vetoes.
- Build the functional labeled DOM failure grid and action controls during the spike. Defer richer keyboard descriptions and screen-reader work until after the renderer decision; the failure grid does not itself establish accessibility acceptance.
- Record any renderer selection in an ADR-002 addendum as **provisional**, conditional on integrated M5 accessibility results. Reopen the choice if keyboard or screen-reader paths cannot meet R6 acceptance.
- Repeat the same crowded movement and pan/zoom sequence in each renderer, foregrounded on the same machine at the agreed viewport and zoom settings. Record p95 frame time, dropped frames, input response, and memory trend after warm-up. Pair these measures with human visual inspection of side-by-side captures and live interaction; numerical timing alone cannot decide the renderer. If both remain smooth, timing differences alone do not displace DOM/SVG.
- The owner and an independent reviewer will inspect paired screenshots and live interaction, marking visual/UI differences acceptable, fixable, or blocking. A repeatable, material visual advantage for Pixi triggers deeper review of its risks, costs, and benefits; a slight preference alone does not select it.
- After the spike, map the `/browser/v2` snapshot and legal-action contract, split setup and match routes while the existing DOM `GameView` works, and then integrate the chosen presentation on the match route. Keep the polished live GUI behind a development switch until two-player, authorized-spectator, prompt, retry, and reconnect checks pass.

## Execution and evidence

1. Build a shared immutable fixture and renderer-neutral coordinate/event-intent seam. Preserve the exact 26×15 geometry, one-square end zones, 4/7/4 row divisions, 64:56 normal and 80:56 large sprite ratios, and unchanged Human/Orc PNGs from the approved MVP requirements. Script the local Blitz presentation without deriving legal actions or outcomes in a renderer.
2. Expose the two pitch renderers side by side on a separate local route or toggle. Keep scoreboard, dugouts, action strip, tooltips and sidebar in DOM. Preserve the existing `/pitch-preview` route. Capture comparable normal and crowded screenshots at 1280×720 and 1920×1080 CSS viewports, 100% and 200% browser zoom, with browser/OS/version, CSS viewport and device scale recorded. Exercise actual-size sampling, overlap, hit testing where art exceeds cells, Fit/zoom/pan, asset failure, Pixi startup failure and context loss.
3. Run the same foregrounded Blitz movement and pan/zoom sequence after warm-up in both renderers. Repeat runs on the same hardware and record p95 frame time, dropped frames, input response and memory trend. Let the owner and independent reviewer inspect paired captures and live interaction without using the timings as a substitute for visual judgment; log their acceptable/fixable/blocking findings separately. A material Pixi visual preference prompts deeper cost/risk review rather than an automatic choice.
4. Capture role-projected, secret-free authoritative snapshots from the Blitz flow for a read-only mapping check. Record any field/role gaps without connecting the parity route to `/browser/v2` or inventing a live outcome.
5. At the five developer-day checkpoint, write a short comparison record and provisional ADR-002 addendum if evidence supports a choice. Preserve the fallback and accessibility conditions. Re-estimate the rest of M5 using the observed work and contract gaps.
6. Then map the live contract, split setup and match routes with the current DOM `GameView`, and integrate the chosen presentation behind a development switch. Remove the switch after the R6-0 handoff checks pass; complete R6-1 through R6-4 and the R6-5 workflow checks for integrated M5 acceptance. The [M4 R6 reference](m4-workstreams-reference.md#r6--desktop-renderer-accessibility-and-content-release-checks) remains the detailed release matrix.

Windows Chrome and Edge are available locally; the owner plans to install Firefox and may obtain a used MacBook or older iPad. NVDA availability remains unconfirmed. Record unavailable browser/assistive-technology combinations as untested rather than passed. An iPad does not satisfy the macOS Safari/VoiceOver desktop matrix. A provisional renderer decision may carry these conditions; integrated M5/R6 release acceptance still requires its declared matrix.

## Existing implementation seams

The M1 Pixi `BoardView` already renders a `Snapshot` without owning command state, but uses fixed 36px cells and has no preview-style Fit/zoom/pan. The DOM/SVG MVP owns its sample players and overlays separately. The spike therefore needs a new shared presentation fixture and coordinate/intent adapter; neither current view is already the common model. The M1 WebGL initialization failure test retains DOM player/destination/action controls, but it does not prove context-loss recovery or a polished DOM pitch fallback. See `browser-client/src/board.ts`, `PitchPreview.tsx`, `pitch-demo.ts`, `main.tsx`, and `test/renderer-failure-demo.mjs`.

The authoritative service exposes `blitz`, `blitzTarget`, `move`, `block`, and pending `blockDie` as server-issued actions rather than a separate pending-die DTO. The live browser handles generic actor-scoped actions and read-only spectator projections. Existing browser evidence covers adjacent block and pending die/reconnect, but not the full movement-then-block Blitz with spectator observation. See `ffb-server/src/main/java/com/fumbbl/ffb/server/match/CoreTurnActions.java`, `CorePromptActions.java`, `browser-client/src/SetupPanel.tsx`, `test/supported-play-demo.mjs`, and `test/v2-client.test.ts`.

## iPad testing note

The current Vite 8 build has no custom browser target and its documented default starts at Safari 16.4, which Apple shipped on iPadOS 16.4. This is a build-compatibility floor, **not** a supported iPadOS minimum for this product: the pinned Pixi/WebGL path, touch behavior, layout, and performance still need device checks. Record the iPad model and exact iPadOS/Safari version if one becomes available; update it to the latest release it supports. An iPad test adds tablet evidence but does not fill the macOS Safari/VoiceOver desktop gap. Set a product iPadOS minimum in M6 only after testing an actual device and deciding mobile support scope. [Vite browser target](https://vite.dev/guide/build); [Safari 16.4 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-16_4-release-notes); [Apple iPadOS compatibility](https://support.apple.com/en-ca/148850).

## Used Mac testing note

The same Safari 16.4 build floor applies to macOS Safari, but macOS has its own version numbers; there is no “iOS minimum” for a MacBook. For a useful current desktop test machine, prefer a used Apple-silicon MacBook that can run the latest macOS and Safari. Apple's macOS 27 compatibility list includes the 2020 M1 MacBook Air and 2020 M1 MacBook Pro as the oldest Air/Pro entries. Verify the exact model before buying. A Mac running only an older OS may still provide diagnostic evidence, but it cannot stand in for the current Safari/VoiceOver acceptance check. [Apple macOS 27 compatibility](https://support.apple.com/en-ca/127255); [Safari update guidance](https://support.apple.com/en-us/102665).
